### F027 — Three public tables have RLS disabled and anon can write to them (lab_panels, derived_metric_definitions, insight_rules)

- Location: `supabase/migrations/20260310054519_full_44_biomarker_panel_schema_v3.sql:123` · severity medium · category rls · owner_action=False

**Evidence**

20260310054519_full_44_biomarker_panel_schema_v3.sql creates lab_panels (:123), derived_metric_definitions (:171) and insight_rules (:216) with no ENABLE ROW LEVEL SECURITY, no policy and no REVOKE, and no later migration touches them (grep over supabase/migrations). 20261006000000_clinical_catalog.sql:241-243 moved the sibling legacy tables into clinical_archive but left these three in public. The repo's own migration comments note that Supabase default privileges give anon and authenticated full DML on new public tables (20261013040000_runtime_config.sql:224), and src/types/supabase.generated.ts:383,634,750 still lists all three. Verification: I applied the 68 migrations that apply in order to a throwaway postgres:15 with those default privileges. relrowsecurity=false for exactly these three public tables. As role anon, an INSERT and an UPDATE on insight_rules, a DELETE on lab_panels and an UPDATE on derived_metric_definitions all succeeded; every write was rolled back. Anyone holding the public anon key can therefore tamper with or bloat these tables. The app takes its rules from code (src/utils/derivedMetrics.ts:106), so the impact is integrity and storage abuse, not a PHI leak.

**Recommendation**

New migration: ENABLE ROW LEVEL SECURITY on all three tables and REVOKE INSERT, UPDATE, DELETE, TRUNCATE FROM anon, authenticated. Keep SELECT with a read policy only if something reads them; otherwise move them into clinical_archive or drop them. Owner: check the production Supabase Security Advisor ('RLS disabled in public') to confirm no other table is affected.

**Verifier's note**

Reproduced independently. I applied supabase/migrations/*.sql in order to postgres:15-alpine with Supabase-style roles and default privileges: 68 of 70 apply. relrowsecurity=false for exactly public.lab_panels, derived_metric_definitions and insight_rules. Role anon held SELECT/INSERT/UPDATE/DELETE/TRUNCATE on all three. Inside a rolled-back transaction, SET ROLE anon then INSERT and UPDATE on insight_rules, UPDATE on derived_metric_definitions and DELETE on lab_panels all succeeded. These tables appear only in the creating migration (:123/:171/:216); git grep finds them only there, in src/types/supabase.generated.ts:383/634/750, and in data-retention-schedule.md:64. clinical_catalog.sql archives only biomarker_definitions, biomarker_reference_ranges and biomarker_phase_ranges. App code reads none of the three, so the impact is unauthenticated tampering and bloat with no PHI. The production state is unverified (owner: Security Advisor).

### F034 — The Stripe entitlement tables, and all PHI tables, keep anon/authenticated DML grants, so RLS is their only lock

- Location: `supabase/migrations/20260217130956_wispy_sky.sql:45` · severity low · category rls · owner_action=False

**Evidence**

stripe_customers, stripe_subscriptions and stripe_orders have RLS with SELECT-only policies (wispy_sky.sql:45-139) and no REVOKE. Yet stripe_user_subscriptions.subscription_status is what grants Plus (_shared/subscription-guard.ts:70-73). The repo's own pattern gives money tables a second, grant-level lock (20260821010000_lock_iap_subscriptions_writes.sql:1-31, and likewise for the claims, beta-tester and complimentary-grant tables). In the throwaway DB, authenticated holds INSERT on stripe_subscriptions, and only the RLS policy rejected an 'active' row. The same rehearsal shows anon still holds SELECT/INSERT/UPDATE/DELETE on lab_reports, biomarkers, report_analytes, period_logs, symptom_logs, interventions and the other PHI tables, so one overly broad policy added later would expose them.

**Recommendation**

REVOKE INSERT, UPDATE, DELETE, TRUNCATE on stripe_customers, stripe_subscriptions and stripe_orders FROM anon, authenticated, and REVOKE ALL FROM anon on every user-data table. Add these tables to factory/sql/verify-privileges.sql.

**Verifier's note**

Verified in the fresh-chain DB. anon and authenticated hold INSERT/UPDATE/DELETE/TRUNCATE on stripe_customers, stripe_subscriptions and stripe_orders, and the only policies are SELECT TO authenticated (wispy_sky.sql). As authenticated, an INSERT of an 'active' stripe_subscriptions row was refused only by RLS, while has_table_privilege(INSERT) is true. anon holds full DML on lab_reports, biomarkers, report_analytes, period_logs, symptom_logs, interventions, cycle_events and others. No policy names anon except app_public_config, biomarker_catalog and processed_stripe_events, the last of which is deny-all. The repo's own rule for money tables (lock_iap_subscriptions_writes.sql:1-31: 'two locks rather than one') is not applied to the Stripe tables. This is defense in depth, and low is right.

### F046 — Stripe billing tables rely on RLS alone; the default client write grants were never revoked

- Location: `supabase/migrations/20260217130956_wispy_sky.sql:45` · severity low · category defense-in-depth · owner_action=False

**Evidence**

stripe_customers, stripe_subscriptions and stripe_orders enable RLS with SELECT-only policies (wispy_sky.sql:45-55, 85-100, 125-140). No migration revokes Supabase's default INSERT/UPDATE/DELETE grants from anon or authenticated: a grep finds no REVOKE or GRANT naming a stripe_ table other than the view grant at :159. Every other table that confers paid access got a second lock: iap_subscriptions (20260821010000_lock_iap_subscriptions_writes.sql:23-31), plus iap_beta_testers, complimentary_entitlements and introductory_deep_access_claims. A row in stripe_customers plus stripe_subscriptions with status 'active' is enough for Premium (entitlement.ts:336). So one over-broad policy, or RLS turned off, would be a free-Premium API. Not exploitable today. Verified by reading the migrations.

**Recommendation**

Add a migration: REVOKE ALL on stripe_customers, stripe_subscriptions and stripe_orders FROM anon; REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER on them FROM authenticated; keep SELECT.

**Verifier's note**

Confirmed. wispy_sky.sql enables RLS on stripe_customers, stripe_subscriptions and stripe_orders with SELECT-only policies, and grep finds no REVOKE on any stripe_ table (the only grant is GRANT SELECT on the view at :159). 20260821010000_lock_iap_subscriptions_writes.sql applies exactly this second lock to iap_subscriptions, on the stated ground that 'every row here is worth money', so the Stripe tables break the project's own pattern. Not exploitable today: RLS denies the writes and PostgREST exposes no TRUNCATE. Defence in depth only.
